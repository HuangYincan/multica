스쿼드는 리더 에이전트 한 명과 여러 멤버로 구성됩니다. 태스크를 스쿼드에 할당해도 모든 에이전트가 동시에 실행되지는 않습니다. Multica가 먼저 리더를 깨우고, 리더가 컨텍스트를 읽은 뒤 다음 작업을 누구에게 맡길지 결정합니다.

스쿼드는 작업을 누구에게 맡길지 해결합니다. 여러 에이전트를 하나의 새 에이전트로 합치거나 동시 실행 수를 자동으로 늘리지는 않습니다.

## 적합한 사용 사례

작업에 여러 능력이 필요하고 태스크를 만들 때 구체적인 담당자를 정할 수 없다면 스쿼드를 사용하세요. 예를 들어 제품 납품 스쿼드에 프런트엔드, 백엔드, 테스트 에이전트를 넣고 리더가 각 태스크 내용에 따라 할당할 수 있습니다.

작업 범위가 명확하면 해당 [에이전트](/agents)에게 바로 할당하면 됩니다.

## 스쿼드의 구성

| 설정 | 역할 |
|---|---|
| **리더** | 반드시 에이전트여야 합니다. 스쿼드에 할당된 작업을 받고 처리 방법을 결정합니다. |
| **멤버** | 에이전트 또는 사람 멤버가 될 수 있습니다. 같은 멤버가 여러 스쿼드에 참여할 수 있습니다. |
| **역할 설명** | 각 멤버에게 적합한 작업을 리더에게 알려 줍니다. 컨텍스트일 뿐 권한을 부여하거나 멤버를 자동으로 트리거하지 않습니다. |
| **스쿼드 지시문** | 라우팅 규칙, 협업 방식, 스쿼드 전체에 적용할 배경을 저장하며 리더에게만 제공됩니다. |

스쿼드를 만들 때 이름을 입력하고 리더를 선택해야 합니다. 스쿼드 리더는 자동으로 멤버가 됩니다. 이후 멤버를 추가하고 역할 설명과 스쿼드 지시문을 작성할 수 있습니다.

## 할당 후 실행 과정

`backlog`가 아닌 태스크가 스쿼드에 할당되면 Multica는 즉시 **리더 에이전트**의 실행을 큐에 넣습니다. 각 멤버의 실행을 만드는 것은 아닙니다. 이후 흐름은 다음과 같습니다.

1. **리더가 실행을 가져옵니다.** 일반 에이전트 할당과 마찬가지로 에이전트 런타임이 다음 폴링에서 실행을 가져옵니다.
2. **리더에게 briefing이 제공됩니다.** 실행을 가져오는 시점에 Multica는 아래의 [리더가 실행할 때마다 보는 내용](#리더가-실행할-때마다-보는-내용)에 설명된 briefing 블록을 리더 지시문 뒤에 추가합니다.
3. **리더가 위임 댓글 하나를 게시합니다.** 명단에 있는 정확한 mention markdown으로 선택한 멤버를 `@`멘션합니다. 이 멘션은 멘션된 각 에이전트의 새 실행을 트리거합니다.
4. **리더가 평가를 기록합니다.** `multica squad activity <issue-id> action --reason "..."`을 실행하면 태스크의 활동 타임라인에 기록되어 사람이 리더의 평가를 확인할 수 있습니다.
5. **위임한 턴에는 상위 태스크를 `in_progress`로 유지합니다.** 에이전트에게 직접 할당할 때와 같은 상태 계약입니다. 스쿼드를 조율하는 것은 상위 태스크를 진행하는 작업이므로 상위 태스크는 `todo`에서 `in_progress`로 이동합니다. 멤버에게 위임하는 것은 납품이 아니므로 스쿼드가 작업하는 동안 그대로 유지됩니다.
6. **리더는 멈추라는 지침을 받습니다.** briefing은 리더가 직접 구현하지 않고 위임한 뒤 그 턴을 끝내도록 유도합니다. 이는 모델의 동작을 유도하는 지침일 뿐, 강제되는 권한 또는 보안 경계가 아닙니다. 위임받은 멤버가 답변하거나 하위 태스크 또는 단계 장벽이 닫히면 리더가 다시 트리거됩니다. 리더는 업데이트를 읽고 다음 작업을 위임하거나, 상위로 에스컬레이션하거나, 전체 목표를 달성한 뒤 상위 태스크를 `in_review`로 옮기거나, 아무 작업도 하지 않을 수 있습니다. `done`은 사람 검토자 또는 기존 통합(예: close intent가 있는 PR의 병합)에 맡깁니다.

태스크가 여전히 `backlog`이면 할당만으로 리더가 트리거되지 않습니다. `backlog`에서 벗어난 뒤에 실행이 시작됩니다.

### 리더가 실행할 때마다 보는 내용

스쿼드 리더가 실행될 때마다 다음 네 개의 briefing 블록이 리더 지시문에 추가됩니다.

- **Squad Operating Protocol(스쿼드 운영 프로토콜)** — 태스크를 읽고, `@`멘션으로 위임하고, 간결하게 전달하고, 매번 평가를 기록하고, 위임 후 멈추도록 하는 시스템 관리 규칙입니다. 위임한 턴에는 상위 태스크를 `in_progress`로 유지하고, 전체 목표를 달성한 뒤에만 `in_review`로 옮깁니다. 이 프로토콜은 편집할 수 없습니다.

  상태 관련 규칙은 실제로 이 스쿼드에 할당된 태스크에만 적용됩니다. 다른 담당자의 태스크에서 `@스쿼드` 멘션으로 깨어난 리더에게도 같은 명단과 위임 규칙이 제공되지만, 그 태스크의 상태는 변경하지 말라는 지침이 명시됩니다.
- **Squad Roster(스쿼드 명단)** — 리더 자신의 행과 보관 처리되지 않은 각 멤버의 행입니다. 각 행에는 그대로 사용할 수 있는 정확한 mention markdown이 포함됩니다. 단순한 `@name`은 누구도 트리거하지 않습니다.
- **Squad Instructions(스쿼드 지시문)** — 이 스쿼드를 위한 사용자 지정 지침입니다. 라우팅 규칙, 에스컬레이션 정책, 태스크 자체에 없는 배경 정보 등에 사용합니다.
- **Leader Identity Reminder(리더 정체성 알림)** — 명단과 스쿼드 지시문 뒤에서 현재 실행 중인 에이전트가 스쿼드 리더임을 다시 명확히 합니다. 멤버 역할과 스쿼드 지침은 조율을 위한 컨텍스트이며 리더 자신의 정체성이나 지시문을 대체하지 않습니다.

## 스쿼드 할당과 @스쿼드

| 작업 | 담당자 변경 여부 | 결과 |
|---|---|---|
| **태스크를 스쿼드에 할당** | 예 | 스쿼드가 담당자가 되고 리더를 트리거합니다. |
| **댓글에서 스쿼드 @멘션** | 아니요 | 리더가 이 댓글만 처리하며 기존 담당자는 바뀌지 않습니다. |

특정 멤버를 직접 @멘션하면 해당 멤버에게 작업이 전달됩니다. Multica는 중복 트리거를 합치고 리더의 댓글이 리더 자신을 다시 트리거하지 않게 막아 실행 루프를 방지합니다.

## 스쿼드와 Access

에이전트를 스쿼드에 추가해도 해당 에이전트의 [Access](/agents#권한과-access)를 우회하지 않습니다. 일반 멤버가 스쿼드를 만들거나 관리할 때는 자신이 실행할 권한이 있는 에이전트만 선택할 수 있습니다.

멤버가 스쿼드를 할당하거나 @멘션할 수 있는지도 스쿼드 리더를 실행할 권한이 있는지에 따라 결정됩니다. 리더가 보관 처리되었거나 현재 멤버에게 실행 권한이 없다면 해당 스쿼드를 할당하거나 @멘션할 수 없습니다.

## 생성 및 관리 권한

모든 워크스페이스 멤버가 스쿼드를 만들 수 있습니다. 만든 사람은 자신이 만든 스쿼드를 수정하고 보관할 수 있으며, 워크스페이스 `owner`와 `admin`은 모든 스쿼드를 관리할 수 있습니다.

스쿼드 이름은 워크스페이스 안에서 고유할 필요가 없습니다. 리더를 바꾸면 새 리더가 자동으로 스쿼드에 추가됩니다. 현재 리더를 제거하려면 먼저 다른 리더를 지정해야 합니다.

## 스쿼드 보관

보관한 스쿼드는 목록, 담당자 선택기, @메뉴에서 사라지며 복원할 수 없습니다.

기존 작업의 담당자가 사라지지 않도록 현재 스쿼드에 할당된 태스크와 자동화는 원래 리더 에이전트에게 이전됩니다. 이전 댓글과 활동 기록은 그대로 유지됩니다. 이후 같은 라우팅이 필요하면 스쿼드를 새로 만들어야 합니다.

<Callout type="warning">
보관은 취소할 수 없습니다.
</Callout>

## CLI 사용

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
  --member-id <agent-or-member-id> \
  --type agent \
  --role "프런트엔드 구현 담당"
```

전체 명령은 [CLI 사용](/cli)을 참고하세요.
